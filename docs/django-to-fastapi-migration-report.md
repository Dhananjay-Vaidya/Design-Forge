# Django → FastAPI Migration Report

Status: **backend swapped and verified for everything the Django backend actually did**
(auth, decisions/alternatives/criteria/scores, deterministic ranking, health, metrics).
Companion documents: `docs/fastapi-migration-audit.md` (inventory + parity matrix),
`docs/adr/ADR-fastapi-database-migration.md`, `docs/adr/ADR-fastapi-authentication.md`,
`FASTAPI_MIGRATION_STATUS.md` (resume-point log).

## Scope: what "parity" means here

The migration brief lists snapshots, scenarios, outcome reviews, dashboard, activity history,
duplication, Gemini analysis and AI job endpoints. **The Django backend never implemented any of
them** (it covered roadmap Phases 1–2 plus observability; there were zero registered Celery tasks
and no `apps.ai` code paths). Migrating "parity" therefore means the features that existed. Those
brief items are unbuilt product work, not migration gaps; the Celery app, the AI/Celery metric
definitions, and the config for Gemini exist so that work can start without re-plumbing. The
brief's Gemini/fake-provider/quota/circuit-breaker requirements (steps 11–12) are **not
implemented**.

## What changed

| Area | Django | FastAPI |
|---|---|---|
| Framework | Django 5 + DRF, gunicorn (sync) | FastAPI, gunicorn + Uvicorn workers |
| ORM / migrations | Django ORM + Django migrations | SQLAlchemy 2 async + Alembic |
| Validation | DRF serializers | Pydantic v2 schemas |
| Passwords | Django PBKDF2 | Argon2id for new hashes; legacy PBKDF2 hashes still verify (proven with a hash generated by real Django) and are upgraded on login |
| Tokens | SimpleJWT + `token_blacklist` app | PyJWT; explicit `refresh_tokens` table (rotation + revocation) |
| CSRF | Django middleware | Hand-rolled double-submit (same `df_csrftoken` cookie / `X-CSRFToken` header) |
| HTTP metrics | `django-prometheus` (`django_http_*`) | ASGI middleware (`decisionforge_http_*`), Prometheus multiprocess mode |
| OpenAPI | drf-spectacular `/api/schema/` | FastAPI `/api/openapi.json`, `/docs`, `/redoc` |
| Celery beat | `django_celery_beat` DB scheduler (no periodic tasks existed) | Removed (nothing scheduled) |
| Django Admin | Enabled, unused by any documented workflow | Not carried over. Replacement CLI scripts: `scripts/create_user`, `scripts/seed_demo` |
| Directory | `backend/` | `backend/`; the old code is `backend_django_legacy/` (rollback only, not run by Compose) |

## What was preserved

Endpoint paths and methods; request field names; response field names (the replay below found and fixed several places where this had drifted); pagination envelope and rules;
status codes; the `{error:{code,message,fields,request_id}}` envelope; auth cookie/CSRF names and
flow; table and column names, constraints and indexes; the deterministic scoring engine
(hand-calculated tests ported; `weighted-sum.v1`); Prometheus job name and scrape target;
Docker Compose service names and `docker compose up --build`.

## Verification of behavioral parity

Two independent kinds of evidence, both actually executed:

1. **Replay against the legacy backend.** `backend/scripts/parity_django_vs_fastapi.py` runs one
   54-step request sequence (auth, CRUD, validation failures, cross-user access, pagination,
   scoring, ranking, deletion) against the real Django backend (run against a scratch copy of the
   database) and the FastAPI backend, diffing status code + normalized body.
   **Result: 44/54 steps identical, 10 documented intentional differences, 0 unexpected.**
   Ranking totals matched exactly (e.g. 0.808081).
2. **Test suite:** 144 tests (unit, integration, API, security, contract, observability).

The replay found real deviations that the FastAPI-only tests had not, and they were fixed:
alternatives/criteria responses used `decision_id` instead of `decision`; score rows used
`alternative_id`/`criterion_id` instead of `alternative`/`criterion`; alternatives/criteria lists
were bare arrays instead of the paginated envelope (the audit itself had this wrong);
`page_size` above 100 was rejected instead of clamped; `page=0`/junk/past-the-end was 400/200 instead
of 404 "Invalid page."; unknown `status` filter was 400 instead of an empty page; and DRF-style
validation wording was lost. Also found: the fresh-database Alembic baseline had server-side
defaults the Django-created schema does not, which made registration fail (HTTP 500) against the
real database while every test passed. Fixed by making defaults Python-side and stripping the
baseline; `tests/integration/test_schema_parity.py` now guards it.

### Intentional differences (10, all listed in the replay script)

- `not_found` message wording: FastAPI says "The requested decision was not found." (Django leaked
  "No Decision matches the given query."). Status and `code` are identical.
- Invalid-token message wording.
- `POST /auth/refresh` without CSRF and a malformed UUID in the path: Django returned HTML error
  pages; FastAPI returns the JSON envelope (same 403 / 404 status).
- Out-of-range score: Django echoed a stringified serializer dict; FastAPI reports
  `scores.0.score`.
- `PATCH /me/profile` with `timezone: 5`: Django silently coerced to `"5"` (200); FastAPI rejects
  it (400). This is the only status-code change.

## Database compatibility

Verified on Postgres 16: (a) fresh empty database → `alembic upgrade head` creates the schema and
`alembic check` reports no drift; (b) a **copy** of the Django-created dev database (with the
Alembic bookkeeping removed to simulate a pure Django DB) → `scripts.db_adopt_existing` verified
the schema, stamped the baseline, applied the two additive revisions (`refresh_tokens`, CHECK
constraints on `status`/`direction`), and kept existing rows. Nothing was dropped or truncated.
The running dev stack uses the real dev database volume, which was never reset.

## Authentication changes

None visible to the frontend: same endpoints, cookie names, CSRF header, and `{user, access}`
shape. Internally: Argon2id + lazy upgrade of legacy hashes, explicit refresh-token table with
rotation, and reuse of a logged-out refresh token is rejected (tested live). Issuer/audience
claims are not used (Django's SimpleJWT did not use them either). Rate limiting on auth
endpoints does **not** exist (it did not in Django either) and is listed under limitations.

## Frontend changes

**None.** See `docs/frontend-fastapi-compatibility.md`. Lint, typecheck, unit tests and the
production build pass unchanged.

## Metrics changes

HTTP metric names changed (no drop-in equivalent exists for the django-prometheus series):

| Old (django-prometheus) | New |
|---|---|
| `django_http_requests_total_by_method_total` | `decisionforge_http_requests_total{method,route,status}` |
| `django_http_responses_total_by_status_total` | `decisionforge_http_requests_total` (label `status` = full code) |
| `django_http_requests_total_by_view_transport_method_total{view}` | `decisionforge_http_requests_total{route}` |
| `django_http_requests_latency_seconds_by_view_method_bucket` | `decisionforge_http_request_duration_seconds_bucket` |

New: `decisionforge_http_requests_in_progress`. Recording rules and the API dashboard were updated
and checked live: the rewritten queries return data in Prometheus, all 25 rules report healthy,
and Grafana provisions all four dashboards. `route` is the matched route template (bounded);
unmatched paths collapse to `unmatched`; a test asserts raw paths, IDs and query strings never
appear as labels. Gunicorn runs 3 workers, so multiprocess mode is on (verified: the
`decisions_created_total` counter aggregates across workers). The `decisionforge_ai_*`,
`celery_*`, sensitivity/scenario/outcome series are *defined* but never emitted; no such features exist yet.

## Tests migrated

All 56 Django tests were mapped by name; every intent is covered (the observability, purity and
scoring tests were recreated; three previously missing intents were added). Added: security
negatives (forged/expired/`alg=none`/wrong-type/deleted-user tokens, every protected route
without a token, cross-user access on every child resource, unknown-field rejection, error
redaction, security headers, trusted hosts, CORS), settings/production validation, schema
parity, OpenAPI snapshot, frontend-call contract, Django-derived pagination/wire-name contract.

## Removed dependencies

Django, djangorestframework, djangorestframework-simplejwt, django-cors-headers, django-environ,
django-filter, drf-spectacular, django-prometheus, django-celery-beat, whitenoise, and Black
(Ruff is the single formatter). The FastAPI stack is Pydantic v2 + pydantic-settings, SQLAlchemy 2
+ asyncpg/psycopg, Alembic, PyJWT, pwdlib (Argon2/bcrypt), prometheus-client, Celery, Redis.
`prometheus-fastapi-instrumentator` was tried and dropped in favour of the small middleware (its
default series were not compatible with the dashboards). `google-genai` and `tenacity` were
*declared* in the legacy requirements but imported nowhere (the `apps/ai`, `apps/outcomes`,
`apps/snapshots`, `apps/activity` packages are empty scaffolds), so they were not carried over;
add them back when the Gemini work starts. `backend_django_legacy/` still contains all the old
packages, deliberately, for rollback.

## Remaining limitations / not done

- **Not implemented** (were never in Django): Gemini/AI, Celery tasks, snapshots, scenarios,
  outcomes, dashboard, activity, duplication, sensitivity as a separate endpoint (sensitivity is
  returned inside the ranking response, as before).
- No rate limiting on auth/write endpoints.
- No Playwright/E2E suite exists in the repository; the end-to-end flow was verified at the API
  level (`scripts/verify_e2e.py`) plus the frontend unit tests, not in a browser.
- The GitHub Actions workflow is written and YAML-validated but has not been run on GitHub.
- `npm ci` (clean frontend install) was not run; the existing installed `node_modules` was used.
- `make prometheus-check` (promtool) fails under Git Bash on Windows because of path mangling in
  the `docker run -v` mount; Prometheus itself loaded and evaluates all rules (verified via its API).
  It works from Linux/macOS/WSL.
- The Nginx upstream item in the brief does not apply: `infrastructure/nginx/` is empty.
- Old Django-era log entries in `IMPLEMENTATION_STATUS.md` are retained as history with a banner.

## Rollback procedure

Nothing is deleted, so rollback is a directory swap. The database needs no rollback: the FastAPI
migrations were additive only (`refresh_tokens` table, two CHECK constraints), and Django ignores
both.

```bash
docker compose down                      # never `-v`
mv backend backend_fastapi
mv backend_django_legacy backend
git checkout <pre-migration-commit> -- docker-compose.yml docker-compose.dev.yml Makefile .env.example \
    infrastructure/prometheus/recording-rules.yml infrastructure/grafana/dashboards/decisionforge-api.json
docker compose up -d --build
```

**Rollback caveat (verified by reading both code paths, not by running a rollback):** accounts
whose password hash FastAPI wrote (new registrations, and legacy PBKDF2 accounts that logged in
once and were upgraded to Argon2id) store a raw `$argon2id$...` hash. Django's hasher expects an
`argon2$`-prefixed hash and `argon2-cffi` is not in the legacy requirements, so those users could
**not** log in after a rollback and would need a password reset. Accounts that have not logged in
since the cutover are unaffected. If rollback safety matters before you cut over production, either
(a) add `argon2-cffi` to the legacy requirements and store hashes in Django's `argon2$` format, or
(b) disable the lazy upgrade in `app/services/auth_service.py` so hashes stay PBKDF2 until you
commit to FastAPI. FastAPI refresh tokens are not valid for Django in either case (users log in again).
